**วันที่:** 26 ตุลาคม 2026
**ขอบเขต:** P1 VENDOR/MONTH FOLDER ROUTING REPAIR + DYNAMIC MULTI-VENDOR DOCUMENT ROUTING
**สถานะรวม: PASS ในระดับการทดสอบ — BLOCKED ในการยืนยันกับระบบจริง**

## สรุปใน 5 บรรทัด

เป้าหมายหลักทำได้แล้ว: **เพิ่มบริษัทใหม่ได้โดยไม่ต้องแก้ source code และไม่ต้อง deploy ใหม่** ยืนยันด้วยการทดสอบทั้งสายจริง (ลงทะเบียนผ่าน API → ส่งเอกสาร → เอกสารเข้าแฟ้มบริษัทใหม่เอง)

ระหว่างทางพบข้อบกพร่องที่มีอยู่เดิม 5 ข้อ ทุกข้อยืนยันด้วยโค้ดก่อนแก้ ข้อที่ร้ายแรงที่สุดคือ **เดือนของแฟ้มคิดจากเขตเวลา UTC** ทำให้เอกสารที่ส่งช่วง 00:00–07:00 ตามเวลาไทยในวันแรกของเดือนลงแฟ้ม "เดือนก่อน"

**ยังไม่ได้ทดสอบกับ production แม้แต่ข้อเดียว** — เข้า production จากที่นี่ไม่ได้ (proxy ปฏิเสธ) และไม่มี GCS credential

## 1. ข้อบกพร่องที่พบ (ยืนยันด้วยโค้ดทุกข้อ)

### 1.1 เดือนของแฟ้มคิดจากเขตเวลา UTC ไม่ใช่เวลาไทย

`build_legacy_path()` เดิม:

```python
monthly = datetime.now(timezone.utc).strftime("%Y-%m")
```

คลินิกอยู่ที่ UTC+7 เอกสารที่ส่งเข้ามาเวลา 01:30 ของวันที่ 1 พฤศจิกายน (เวลาไทย) คือ 18:30 ของวันที่ 31 ตุลาคม ตามเวลา UTC → ระบบลงแฟ้ม `2026-10` ทั้งที่ควรเป็น `2026-11`

พิสูจน์:

```
31 ต.ค. 18:30 UTC → เดือนแบบ UTC    = 2026-10   (เดิม)
                   → เดือนแบบไทย     = 2026-11   (ถูกต้อง)
```

### 1.2 `build_document_path` ทิ้งค่า `date` ที่ส่งมาสำหรับบิล

```python
return build_legacy_path(folder, filename, subfolder)   # ไม่ส่ง date ต่อ
```

`build_legacy_path` เดิมไม่มีพารามิเตอร์ `date` เลย ผู้เรียกที่ส่ง `date=doc_dt` มาเพื่อรักษาเดือนเดิมจึงถูกเพิกเฉยเงียบๆ ผลคือ **การประมวลผลซ้ำ (retry), การรวมเอกสารหลายหน้า, และการจัดประเภทใหม่ ได้เดือนตามเวลาที่ประมวลผล ไม่ใช่เดือนที่ผู้ส่งส่งเข้ามา**

### 1.3 เส้นทางจัดประเภทใหม่ไม่ส่งแฟ้มบริษัทเลย

`_reclassify_document()` เดิม:

```python
new_path = build_document_path(
    dest_folder, filename, new_category, patient_folder=patient_folder,
)   # ไม่มี subfolder
```

บิลที่ผู้ดูแลจัดประเภทด้วยมือจึงลงที่ `02_BILLS_RECEIPTS/YYYY-MM/` ตรงๆ ไม่มีแฟ้มบริษัท — โครงสร้างแฟ้มในระบบจึงมีสองแบบปนกัน

### 1.4 รายชื่อบริษัท hardcode ไว้ใน server.py

`BILL_COMPANY_REGISTRY` เป็น dict ในไฟล์ `server.py` การเพิ่มบริษัทใหม่ต้องแก้โค้ดแล้ว deploy ใหม่ทุกครั้ง — ขัดกับเป้าหมายของงานนี้โดยตรง

### 1.5 `detect_bill_company` ตัดสินจาก keyword เพียงคำเดียว

```python
if hits > best_hits: best_company = company
if best_hits > 0: return best_company     # 1 hit ก็พอ
```

ตารางเดิมปน **ชื่อบริษัท** กับ **ชื่อสินค้า** ไว้ด้วยกัน (`"agani needle"`, `"kdl 3ml syringe"`, `"supernova"`) เอกสารที่เอ่ยถึงสินค้ารุ่นหนึ่งจึงถูกจัดเข้าแฟ้มบริษัทนั้นทันที ทั้งที่สินค้ารุ่นเดียวกันอาจปรากฏในเอกสารของบริษัทอื่น และบริษัทที่ไม่รู้จักถูกเหมารวมเป็น `"OTHER"` โดยไม่มีใครรู้ว่าต้องตรวจ

### 1.6 (พบโดยไม่คาด) NFKC ทำให้คำว่า "จำกัด" ไม่เคยถูกตัดออก

การทำให้ชื่อบริษัทเป็นรูปแบบเทียบกันได้ใช้ `unicodedata.normalize("NFKC", ...)` แล้วตัดคำบอกรูปแบบนิติบุคคล แต่ **NFKC แยก "ำ" (U+0E33 SARA AM) ออกเป็น U+0E4D + U+0E32** คำว่า `"จำกัด"` ที่เขียนด้วย U+0E33 ในรายการคำที่จะตัดจึงไม่เคย match ข้อความที่ normalize แล้ว

ผลคือ `"บริษัท เมดิท็อป จำกัด"` กลายเป็น `"เมดิท็อปจํากัด"` ไม่ใช่ `"เมดิท็อป"` — ชื่อบริษัทไทยที่เขียนต่างรูปจึงเทียบกันไม่ตรง

พิสูจน์:

```python
>>> "ำ" in unicodedata.normalize("NFKC", "จำกัด")
False
```

## 2. สิ่งที่แก้

### 2.1 โมดูลใหม่ `vendor_registry.py` (1,397 บรรทัด)

ทะเบียนบริษัทย้ายจาก source code ไปอยู่บน GCS ที่ `_vendors/registry.json` (เขียนเป็นไฟล์ versioned ไม่ลบไฟล์เก่า) โครงสร้างตามแบบเดียวกับ `MasterPatientRegistry` ที่ใช้งานอยู่แล้ว

`VendorRecord` เก็บ: `vendor_id`, `canonical_name` (ชื่อแฟ้ม), `display_name` (ชื่อเต็มตามหนังสือรับรอง), `aliases` (ไทย/อังกฤษ), `tax_id`, `verified`, `active`, `created_at/by`, `updated_at/by`, `notes`

**ลำดับการจับคู่** ตามข้อกำหนด:

| ลำดับ | วิธี | จัดเก็บอัตโนมัติ |
|---|---|---|
| 1 | เลขผู้เสียภาษี 13 หลักครบถ้วน | ✅ |
| 2 | ตรง alias ที่อนุมัติไว้ | ✅ |
| 3 | ชื่อไทย/อังกฤษหลัง normalize | ✅ |
| 4 | ความคล้าย (fuzzy) | ❌ เสนอให้คนยืนยัน |
| 5 | ไม่พบ | ❌ เข้าแฟ้มตรวจสอบ |

**ข้อ 5 ของข้อกำหนด (AI-assisted interpretation) ไม่ได้ทำโดยเจตนา** — `EXTERNAL_AI_CLASSIFICATION_ALLOWED = False` การส่งเนื้อหาเอกสารไป External AI ขัดนโยบาย PDPA ของระบบนี้ จึงใช้การตรวจโดยคนแทน ซึ่งปลอดภัยกว่าและไม่ลดคุณภาพผลลัพธ์ เพราะเอกสารที่ AI ต้องตีความคือเอกสารที่ไม่ควรจัดเก็บเองอยู่แล้ว

### 2.2 เดือนและเขตเวลา

เพิ่ม `to_bangkok()` / `bangkok_month()` ใน `quarterly_compare.py` และให้ **ทุกหมวดเอกสาร** คิดเดือน/ไตรมาสตามปฏิทินไทย — ไม่ให้มีสองมาตรฐานในระบบเดียว

`build_legacy_path()` รับ `date` แล้ว และ `build_document_path()` ส่งต่อให้

### 2.3 ที่มาของเดือนคือเวลาที่ผู้ส่งส่งเข้ามา

ร้อย `timestamp` จาก LINE event ลงมาตลอดสาย:

```
webhook (event["timestamp"])
  → _async_process_image / _async_process_file
    → _handle_incoming_document
      → (multi-page buffer เก็บเวลาของ "หน้าแรก")
        → process_file_async
          → build_object_metadata  (metadata["submitted_at"])
            → GCSStorage.save      (date= ที่ส่งให้ builder)
```

`parse_line_timestamp()` ปฏิเสธเวลาที่เพี้ยน (ก่อนปี 2020 หรืออนาคตเกิน 1 วัน) แล้ว fallback ไปเวลาปัจจุบัน — เวลาที่ผิดจะทำให้เอกสารไปอยู่เดือนที่ไม่มีอยู่จริง

`_doc_submitted_date()` เป็นจุดเดียวที่ตัดสินวันที่ของเอกสารใน index ใช้ `submitted_at` ก่อน แล้วค่อย `upload_date` โดย **ตรึงวันที่ล้วนไว้ที่เที่ยงวันตามเวลาไทย** เพื่อไม่ให้การเปลี่ยนเขตเวลาทำให้ระบบคิดว่าเอกสารเก่าทุกใบที่ลงวันที่ 1 ต้องย้ายแฟ้ม

### 2.4 เส้นทางจัดเก็บเหลือทางเดียว

ทั้งสามเส้นทาง (อัตโนมัติ, จัดประเภทใหม่, retroactive routing) เรียก `build_document_path()` เดียวกัน และบิลทุกเส้นทางเรียก `resolve_bill_vendor()` เดียวกัน

### 2.5 ชื่อแฟ้มปลอดภัยด้วย allowlist

ชื่อแฟ้มบริษัทรับเฉพาะ `[A-Z0-9_]` และอักษรไทย `[฀-๿]` ยาว 2–40 ตัว ไม่ขึ้นต้นด้วย `_` และไม่ใช่ชื่อที่ Windows สงวนไว้ (CON, PRN, NUL, COM1–9, LPT1–9)

การใช้ allowlist ทำให้ path traversal และอักขระที่ Windows ห้าม `< > : " | ? *` **เป็นไปไม่ได้โดยโครงสร้าง** ไม่ต้องไล่ลบทีละตัว

**อนุญาตอักษรไทยในชื่อแฟ้ม** เพราะบริษัทคู่ค้าหลายรายมีชื่อไทยล้วน ถ้าบังคับ ASCII ผู้ดูแลจะได้แฟ้มเป็นรหัสที่อ่านไม่รู้ความ ระบบนี้สร้างแฟ้มผู้ป่วยเป็นภาษาไทยอยู่แล้ว (`57042_สมชาย`) และ Windows รองรับ Unicode ในชื่อโฟลเดอร์เต็มรูปแบบ

`_safe_folder_component()` ใน `quarterly_compare.py` เสริมให้กันอักขระควบคุม อักขระที่ Windows ห้าม และชื่อสงวน และ `copy_to_category()` ส่ง subfolder ผ่านตัวนี้ก่อนต่อเป็น path บนดิสก์

### 2.6 ผู้ซื้อ vs ผู้ขาย

`split_supplier_section()` แบ่งเอกสารที่คำว่า `ลูกค้า / ผู้ซื้อ / ผู้รับสินค้า / Bill To / Ship To / Customer` แล้วหาชื่อบริษัทเฉพาะในส่วนหัว (ฝั่งผู้ขาย)

`BUYER_SELF_NAMES` กันชื่อคลินิกและโรงพยาบาลระนองไว้ ไม่ให้ถูกจับเป็นบริษัทคู่ค้าในทุกกรณี

### 2.7 ไม่รวมบริษัทที่ชื่อคล้ายกัน

จับคู่กับ **ชื่อนิติบุคคลที่ดึงออกมาได้** ไม่ใช่ค้นในข้อความทั้งก้อน และต้องตรงทั้งชื่อ หรือ alias กินพื้นที่ชื่อนั้น ≥ 75%

ตัวอย่างที่กันได้: `"THAI WATER SUPPLY"` (15 ตัวอักษรหลัง normalize) กับ alias `"thai water"` (9) ได้สัดส่วน 0.60 < 0.75 → **ไม่จับคู่ เข้าแฟ้มตรวจสอบ** ทั้งที่ชื่อขึ้นต้นเหมือนกัน

การค้นในข้อความทั้งก้อนใช้เฉพาะเมื่อดึงชื่อนิติบุคคลไม่ได้เลย และรับเฉพาะ alias ยาว ≥ 12 ตัวอักษร

ถ้าตรงหลายบริษัท → ไม่เดา ส่งรายชื่อผู้ต้องสงสัยให้ผู้ดูแล

### 2.8 กันแฟ้มซ้ำตอนลงทะเบียน

`find_conflicts()` ตรวจสามแบบก่อนรับลงทะเบียน:

- เลขผู้เสียภาษีซ้ำ → **ปฏิเสธ** (เป็นบริษัทเดียวกันแน่นอน)
- alias หลัง normalize ซ้ำพอดี → **ปฏิเสธ**
- ชื่อคล้ายเกินเกณฑ์ → **ปฏิเสธจนผู้ดูแลยืนยันด้วย `allow_similar`**

ทำให้ `"บริษัท เอ จำกัด"` กับ `"บจก. เอ"` ไม่กลายเป็นสองแฟ้ม

### 2.9 Endpoint ผู้ดูแล (ยืนยันด้วย header เท่านั้น)

| Endpoint | หน้าที่ |
|---|---|
| `GET /admin/api/v2/vendors/list` | รายชื่อบริษัททั้งหมด |
| `POST /admin/api/v2/vendors/suggest` | วิเคราะห์เอกสาร เสนอชื่อแฟ้ม + เตือนถ้าอาจซ้ำ |
| `POST /admin/api/v2/vendors/register` | **ลงทะเบียนบริษัทใหม่** |
| `POST /admin/api/v2/vendors/update` | แก้ alias / เลขภาษี / ยืนยัน / ปิดใช้งาน |
| `GET /admin/api/v2/vendors/review-queue` | บิลที่ระบุบริษัทไม่ได้ |
| `GET /admin/api/v2/vendors/relocation-plan` | แผนย้ายไฟล์เดิมแบบ dry-run |

Endpoint ใหม่ทั้งหมดรับ secret ทาง header `X-Admin-Secret` เท่านั้น **ไม่รับทาง query string** และใช้ `hmac.compare_digest`

> **ข้อเสนอแนะ:** endpoint เดิมในระบบ (`hn-registry`, `master-registry`) ยังรับ secret ทาง `?secret=` ซึ่งถูกบันทึกใน access log ของ proxy และ Render ผมไม่แก้ของเดิมเพราะอาจทำให้เครื่องมือที่คุณหมอใช้อยู่พัง — ถ้าต้องการให้แก้ บอกได้

### 2.10 ไม่นำข้อความที่ไม่ได้ตรวจไปเป็น path

ชื่อแฟ้มบริษัทมาจากทะเบียนเท่านั้น ค่าที่ผู้จำแนกส่งกลับมา (`result["bill_company"]`) ถูกตรวจสองชั้นก่อนใช้: ต้องผ่าน `is_valid_canonical_name()` **และ** ต้องมีอยู่ในทะเบียนจริง ถ้าไม่ผ่านจะ log เตือนแล้วไประบุจากข้อความ OCR ผ่านทะเบียนใหม่

สำคัญถ้าในอนาคตเปิดการจำแนกด้วย AI — ค่านั้นคือข้อความอิสระจากโมเดล

### 4.2 การทดสอบทั้งสาย (end-to-end) ผ่าน `process_file_async` จริง

```

  [2] 30 ก.ย. 18:30 UTC = 1 ต.ค. 01:30 ไทย   -> 02_BILLS_RECEIPTS/NIKKISO/2026-10
  [3] บริษัทใหม่ยังไม่ลงทะเบียน              -> 02_BILLS_RECEIPTS/_PENDING_REVIEW/2026-10
  [4] ชื่อคล้ายคนละบริษัท                    -> 02_BILLS_RECEIPTS/_PENDING_REVIEW/2026-10

=== ลงทะเบียนบริษัทใหม่ผ่าน API: 200 ===
  [5] ส่งหลังลงทะเบียน                       -> 02_BILLS_RECEIPTS/SUNRISE_MEDICAL/2026-10

```

## 5. แผนย้ายไฟล์เดิม (dry-run — ยังไม่ดำเนินการ)

`GET /admin/api/v2/vendors/relocation-plan` คำนวณว่าบิลแต่ละใบ "ควร" อยู่ที่ใด **อ่านอย่างเดียว ไม่คัดลอก ไม่ย้าย ไม่ลบ ไม่แก้ index**

ตัวอย่างผลจากข้อมูลทดสอบ:

```
to_move=1  already_correct=1  needs_vendor_review=1

  doc aaa11111  vendor=NIKKISO (tax_id)
    เดิม   : 02_BILLS_RECEIPTS/2026-10/old1.jpg
    ใหม่   : 02_BILLS_RECEIPTS/NIKKISO/2026-10/old1.jpg
    windows: 02_BILLS_RECEIPTS\NIKKISO\2026-10\old1.jpg
    sha256 : cccccccccccccccc…   ชนกัน: False
```

คุณสมบัติที่ทดสอบไว้:

- เอกสารที่อยู่ถูกแฟ้มแล้ว ไม่อยู่ในแผน
- เอกสารที่ระบุบริษัทไม่ได้ **ไม่ถูกย้ายโดยเดา** (นับแยกเป็น `needs_vendor_review`)
- เอกสารที่ไม่ใช่บิล ไม่ถูกแตะ
- เดือนเดิมคงอยู่ ไม่ย้ายข้ามเดือน
- path ฝั่ง Windows เป็น **relative ไม่มี drive letter** เพราะ sync root ตั้งที่เครื่องคลินิก ไม่เดาและไม่ hardcode
- บอกวิธี rollback ไว้ในผลลัพธ์

**ยังไม่ได้ทำส่วน "ย้ายจริง" โดยเจตนา** ตามข้อกำหนดที่ว่าต้องได้รับอนุมัติก่อน เมื่อคุณหมออนุมัติ จะใช้วิธีเดียวกับคำสั่ง "ย้ายเอกสาร" ที่มีอยู่แล้ว คือ **คัดลอกแล้วอัปเดต index โดยไม่ลบไฟล์ต้นฉบับ** (ระบบไม่มีสิทธิ์ `storage.objects.delete` อยู่แล้ว)

## 6. ขั้นตอน rollback

ทุกขั้นย้อนกลับได้ ไม่มีการลบข้อมูล

| ต้องการย้อน | วิธี |
|---|---|
| ทั้งหมด (โค้ด) | `git revert <commit>` แล้ว deploy — ทะเบียนบน GCS ไม่ถูกแตะ เอกสารที่เก็บไปแล้วยังอยู่ที่เดิม |
| ทะเบียนบริษัท | ไฟล์เขียนเป็น `_vendors/registry_v<timestamp>.json` ไม่ลบของเก่า — คัดลอกเวอร์ชันก่อนหน้าทับ `_vendors/registry.json` |
| ปิดบริษัทที่ลงทะเบียนผิด | `POST /admin/api/v2/vendors/update` ด้วย `{"active": false}` — ไม่ลบข้อมูลและไม่แตะเอกสารเดิม |
| กลับไปใช้เดือนแบบ UTC | ไม่แนะนำ แต่ทำได้โดยแก้ `to_bangkok()` ใน `quarterly_compare.py` ให้คืนค่าเดิม |

เอกสารที่เก็บไปแล้วไม่ถูกย้ายโดยอัตโนมัติในทุกกรณี

## 7. พฤติกรรมที่เปลี่ยน — ต้องให้คุณหมอรับทราบ

### 7.1 บิลที่ระบุบริษัทไม่ได้ จะเข้าแฟ้ม `_PENDING_REVIEW` แทน `OTHER`

เดิมเอกสารที่ไม่ตรงบริษัทใดถูกเหมารวมเป็น `OTHER` และเอกสารที่ตรง keyword สินค้าเพียงคำเดียวถูกจัดเข้าแฟ้มบริษัทนั้นทันที

ตอนนี้เอกสารที่ยังมั่นใจไม่พอเข้าแฟ้มตรวจสอบ และมีคิวให้ดูที่ `/admin/api/v2/vendors/review-queue` **ผลข้างเคียง: ช่วงแรกจะมีเอกสารเข้าคิวตรวจมากกว่าเดิม** ซึ่งเป็นไปตามข้อกำหนดที่ว่า "บริษัทไม่รู้จักต้องเข้าคิวตรวจ ไม่ใช่ถูกจัดเข้าแฟ้มที่อาจผิด" ยิ่งลงทะเบียนบริษัทครบ คิวยิ่งสั้น

### 7.2 เอกสารคลินิกคิดเดือนตามปฏิทินไทยด้วย

ผมเปลี่ยนให้ผลแล็บ/ใบยา/ใบฟอกเลือดใช้ปฏิทินไทยเหมือนบิล เพื่อไม่ให้มีสองมาตรฐานในระบบ

**กระทบเฉพาะเอกสารที่ส่งช่วง 00:00–07:00 ตามเวลาไทย ในวันแรกของเดือน** ซึ่งจะไปอยู่เดือนที่ถูกต้องแทนเดือนก่อน เอกสารเก่าที่เก็บไปแล้วไม่ถูกย้าย

ถ้าคุณหมอเห็นว่าควรคงเอกสารคลินิกไว้แบบเดิมก่อน บอกได้ — แก้จุดเดียว

## 8. ที่ยังทำไม่ได้ / ควรทำต่อ

1. **ย้ายไฟล์เดิมที่วางผิดแฟ้ม** — มีแผน dry-run แล้ว รอคุณหมออนุมัติจึงทำส่วนย้ายจริง
2. **ยืนยันกับ production** — ต้องรัน `/admin/api/v2/vendors/relocation-plan` กับข้อมูลจริง เพื่อรู้ว่ามีบิลที่วางผิดแฟ้มกี่ใบ
3. **ลงทะเบียนบริษัทที่เหลือ** — ตอนนี้มี 9 รายจากตารางเดิม ถ้ามีคู่ค้ารายอื่นที่ส่งบิลเข้ามา ลงทะเบียนเพิ่มได้เองผ่าน API
4. **หน้าเว็บจัดการบริษัท** — ตอนนี้มีแต่ API ยังไม่มีหน้าเว็บ ถ้าคุณหมอต้องการหน้าจอกดได้ ทำเพิ่มได้
5. **หนี้เทคนิคที่พบ (มีอยู่ก่อน ไม่ใช่ของงานนี้):** `test_security.test_valid_signature_accepted` ล้มเมื่อรันชุดทดสอบย้อนลำดับตัวอักษร ยืนยันแล้วว่าล้มบนโค้ดเดิมด้วย (`git stash` แล้วรันซ้ำ) CI รันเรียงตามตัวอักษรจึงผ่าน แต่เป็นความเปราะที่ควรแก้
6. **Endpoint เดิมรับ secret ทาง query string** — ดูข้อ 2.9
